## 1. サービスの概要

| 項目 | 内容 |
|---|---|
| サービス名 | ポイフォ（POIFO）。由来は POINT × FOLLOW |
| ブランドコピー | あなたのポイ活を、フォロー。 |
| トップの訴求コピー | ひとりじゃない、あたらしいポイ活。 |
| 対象 | スマホで使う個人。初動〜100人、最大1,000人程度を想定 |
| ASP | GF Rewards（1社）。案件の取り込みと成果通知（ポストバック）で連携する |

通常のポイントサイトのように自由に案件を探して使えることに加え、公式LINEで担当スタッフに相談でき、イベントでみんなでポイ活に取り組める。

### 1.1 役割分担

| やること | どこでやるか |
|---|---|
| 案件を探す・使う、ポイントを貯める・交換する | サイト（このシステム） |
| 個別の相談・初回面談の日程調整・フォロー | ポイフォ公式LINE（担当者が手で対応）。サイトからはリンクで遷移するだけ |
| イベントの紹介・参加受付・参加ポイントの付与 | サイト |
| 友達紹介の記録・紹介報酬の計算と付与（[15章](#15-友達紹介2026-11-28-先方案を受領条件は仮)） | サイト |
| イベント当日のやりとり・案内 | LINE オープンチャット（イベントごとのサブトークルーム） |

ロゴ・色・キャラクターの扱いは [../brand/README.md](../brand/README.md)。

## 2. 全体の前提

- サイトは3つの入口に分かれる
  - 会員サイト（`<domain>`）: Astro の静的ページ。変わるデータ（案件・イベント・ポイントなど）はブラウザから API を呼んで表示する
  - API（`api.<domain>`）: 会員サイトから使う API、LINE ログイン、案件への遷移、成果通知の受信
  - 管理画面（`admin.<domain>`）: 運営が使う画面。IP 制限をかける
- 会員のログインは LINE ログインだけ（パスワードは持たない）。ログイン状態は Cookie で持つ
- 会員のメールアドレスは連絡用に持つ（ログインには使わない。[3.5](#35-メールアドレス2026-11-28-未実装)）
- 管理者のログインはメールアドレス＋パスワード＋認証アプリの6桁コード（必須）
- 1ポイント＝1円（`POIFO_YEN_PER_POINT`）
- 日時は日本時間で扱う

## 3. 会員

### 3.1 会員登録・ログイン

1. 会員サイトの「LINEで始める」「ログイン」から LINE ログインへ進む（登録とログインは同じボタン）
2. LINE の同意画面で許可すると、初めての人はその場で会員になる（入力する項目はない）
   - LINE のユーザーID・表示名・アイコンを保存する
   - ASP に渡す会員ID（`uid`、ULID）を発行する。LINE のユーザーIDは ASP に渡さない
3. LINE ログインの画面で、公式LINE の友だち追加も案内する（任意。追加しなくてもサイトは使える）
4. 会員サイトに戻る。初めての人には登録完了と公式LINE の案内、2回目以降は「ログインしました」を出す

ログインできない場合（キャンセル・期限切れ・LINE との通信失敗・退会済み・停止中）は理由をエラー画面に出す。

### 3.2 会員の状態

| 状態 | 意味 | できること |
|---|---|---|
| 有効 | ふつうの会員 | すべて |
| 停止中 | 管理者が停止した | ログインできない。ログイン中でも次の API 呼び出しでログアウトされる。案件への遷移・口座の登録・換金申請・イベント参加ができない。成果通知は台帳に記録する（扱いは運営が調査して決める） |
| 退会済み | 会員が退会した | 何もできない。同じ LINE アカウントでは再登録できない |

- 停止には理由（255文字まで）が必須。理由は操作ログに残し、会員には見せない
- 再開すると元どおり使える。退会済みの会員は停止・再開できない

### 3.3 マイページ

2026-11-26 に参考サイトの構成に合わせて組み直した（画面は [screen-spec.md](screen-spec.md) S09・S12・S20・S21）:

- 表示名、ポイント（利用可能／判定中）、ポイント交換へのリンク、公式LINE の友だち追加リンク
- マイページを「ポイント通帳」にし、明細（ポイント履歴）・交換履歴・案件の利用履歴をタブで見られるようにする
- 案件の利用履歴は、「この案件に進む」の記録（`campaign_clicks`）を会員に見せる。直近90日（IP・ブラウザ情報は見せない）。会員 API は `GET /v1/me/clicks`
- 会員ID（`uid`）・登録日・振込先口座・退会は「登録情報」ページにまとめる。`GET /v1/me` が会員ID・登録日も返す

### 3.5 メールアドレス（2026-11-28、未実装）

先方のデザイン案にログイン後のメールアドレス登録の案内が入るため、会員のメールアドレスを持つことにした（それまでは「持たない」）。**ログインには使わない**（ログインは LINE だけのまま）。

**使い道**
- 換金（ポイント交換）の受付・振込完了・却下の連絡
- LINE アカウントを失った人の本人確認（[14章](#14-まだ決まっていないこと) #3 の付け替えの手がかり）
- 重要なお知らせ（規約の変更など）
- お得情報・キャンペーンのメールは、本人が「受け取る」にしたときだけ送る（特定電子メール法。既定は受け取らない）

**登録のしかた**
1. 会員が自分で入力する（LINE からメールアドレスを受け取る権限は使わない。理由: LINE Developers での申請が要る、LINE にメールを登録していない人・許可しない人がいる、LINE と違うアドレスで受け取りたい人がいる）
2. 入力したアドレスに確認メールを送り、メールのリンク（24時間有効）を開いたら「確認済み」にする。確認前のアドレスには連絡を送らない
3. 変えるときも同じ（確認が済むまでは古いアドレスのまま）
4. 同じアドレスを別の会員が確認済みで使っていたら登録できない（「このメールアドレスは登録できません」。どの会員かは出さない）
5. 確認メールの再送は1時間に3回まで

**必須にするか**
- **必須**（2026-11-28 先方の「初回登録」画面イメージと yamada さんの指示）。LINE ログインのたびに、メールアドレスを入れていない会員は「初回登録」画面（S27）へ移す
- 画面を見て回ることはできるが、**メールアドレスを入れるまで案件に進めない**（案件詳細の「この案件に進む」を押せなくし、S27 への案内を出す。API の遷移 `/go/{案件}` も S27 へ移す）
- 入れていない会員には、ログイン中のトップの一番上に警告の帯を出す（S01）
- 確認メールのリンクを開くまでは「確認待ち」。案件には進めるが、**換金の申請には確認済みが必要**
- 振込先口座は同じ画面で「今はスキップする／続けて口座を登録する」を選ぶ（任意）
- 紹介URLから来た人の紹介元は、LINE ログインで会員を作った時点で記録する（[15.2](#152-紹介のひもづけ)）。初回登録の画面より前なので、ここでは何もしない
- すでに会員でメールアドレスがない人（公開前のテスト会員）は、次のログインで初回登録の画面になる

**送る仕組み**
- Amazon SES（管理者アラートと同じ）。会員に送るには SES のサンドボックス解除（本番利用の申請）が要る（14章 #23）。解除までは確認メールが届かないので、公開前に済ませる（送れなかったときも登録は進め、S21 から再送できる）
- 退会したらメールアドレスを消す

### 3.4 退会

- マイページから、注意事項に同意して退会する
- **手続き中の換金申請（審査中・振込準備中）があるときは退会できない**（振込が終わってから。交換先が増えても、どれか1つでも手続き中ならできない）
- 退会すると
  - 残っているポイント（利用可能・判定中とも）は失効する。台帳はそのまま残す
  - 退会後に届いた成果通知は記録だけして、ASP に「退会ユーザー（`2`）」を返す
  - ログアウトし、同じ LINE アカウントでは再登録できない（不正対策。LINE のユーザーIDは残す）
  - 表示名・アイコンは消す。口座情報は同一口座の検知のために残す（画面には出ない）
- 退会は取り消せない（運営に依頼されても戻さない。仮）

## 4. 案件

### 4.1 取り込み

- GF Rewards の案件連携 API から15分ごとに全件取り込み、DB に保存する（API は1時間60回までなので、サイトからは直接呼ばない）
- 案件名・カテゴリ・対応端末・アイコン・ポイント・掲載期間・説明・成果条件・成果地点（地点ごとのポイントと承認までの日数）・計測リンクを保存する
- ポイントは ASP が計算した値をそのまま使う（サイト側で率を掛けない）

### 4.2 掲載

- 会員サイトに出すのは「ASP 側で掲載中」かつ「掲載期間内」かつ「運営が非表示にしていない」案件
- 並びは「おすすめ → 並び順 → 新しい順」
- 一覧はカテゴリで絞り込める。カテゴリは ASP の値をそのまま使い、掲載中の案件があるものだけ件数つきで出す
- トップの案件メニュー（2026-11-27 デザイン更新。画面仕様 S01）から、次の5つの一覧を開ける。ASP のカテゴリは「アプリインストール」「無料会員登録」のような成果の種類で、ゲームかどうか・初心者向けかどうかは分からないため、特集は運営が管理画面で印を付けて決める
  - おすすめ: 「おすすめ」の案件だけ（API `featured=1`）
  - はじめて向け・ゲーム案件特集・みんなで挑戦中: その印が付いた案件だけ（API `tag=beginner`／`game`／`together`）。並びは通常と同じ
  - 高還元: 掲載中の全案件を最大ポイントの多い順（API `sort=points`）。定率でポイントが決まっていない案件は最後。同じポイントなら通常の並び
- 一覧は1ページ20件（最大50件）
- 案件の閲覧はログインしなくてもできる

### 4.3 表示設定（管理画面）

案件の中身は ASP から取り込むので管理画面では変えない。運営が決めるのは表示の仕方だけ。

| 設定 | 内容 |
|---|---|
| 非表示 | オンにすると、ASP 側で掲載中でもサイトに出さない |
| おすすめ | オンにすると、一覧の先頭とトップのおすすめ枠に出す |
| 特集の印 | 「はじめて向け」「ゲーム案件特集」「みんなで挑戦中」を案件ごとにいくつでも付けられる。付けた案件がトップの案件メニューのその一覧に出る（2026-11-27） |
| 並び順 | 数字が小さいほど前に出す（既定 0） |

- 管理画面の一覧の絞り込み: 掲載状態（サイトに掲載中／ASP 側で停止・未開始／掲載終了／非表示）、名前・案件IDの検索
- 一覧で案件ごとに、ASP の状態・掲載期間・最大ポイント・最終取り込み日時を表示する
- 変更は操作ログに残す

### 4.4 案件への遷移

1. 会員が案件詳細の「この案件に進む」を押す
2. API（`/go/{案件}`）がクリックを記録し（会員・案件・IP・ブラウザ情報）、計測リンクに `user_id=<uid>` を付けて広告主のページへ移動する
3. ログインしていなければログイン画面へ（ログインしないとポイントが付かないため）。停止中の会員は進めない。メールアドレスが未登録の会員は初回登録（S27）へ移す（[3.5](#35-メールアドレス2026-11-28-未実装)、未実装）

### 4.5 お気に入り（2026-11-26 yamada 決定）

会員が気になる案件を保存しておき、あとでまとめて見られるようにする（参考サイトの「お気に入り広告一覧」にあたる）。

- 案件カード・案件詳細の「お気に入り」ボタンで登録・解除する。ログインが必要（未ログインで押したらログイン画面へ）
- 1人200件まで。超えたら「お気に入りは200件までです。」で登録できない。登録できるのは掲載中の案件だけ（解除は掲載終了後もできる）
- 登録・解除は会員ごとに1分60回まで
- お気に入り一覧（画面仕様 S24）は登録の新しい順。掲載が終わった・非表示にした案件も一覧に残し、「掲載終了」と出して「この案件に進む」は出さない（会員が自分で解除できる）。もう一度掲載されたら元どおり出す
- 案件の一覧・詳細の API は、ログイン中なら各案件に「お気に入り登録済みか」を付けて返す
- 停止中の会員は登録・解除できない。退会した会員のお気に入りは残すが使われない
- 管理画面の案件一覧に、案件ごとのお気に入り数を出す（おすすめ設定の参考にする）
- 会員 API: `GET /v1/me/favorites`（一覧）、`PUT /v1/me/favorites/{案件}`（登録）、`DELETE /v1/me/favorites/{案件}`（解除）。同じ案件を2回登録してもエラーにしない

### 4.6 動作確認用のダミー案件（2026-11-27 yamada 決定）

GF Rewards の取り込みが動くまで、実際の画面で一覧・詳細・お気に入りの動きを確かめるために使う。ステージングがないので本番の DB に入れる。サーバでコマンドを打てない場所からでも使えるよう、管理画面のボタンで入れる・消す。

- ダミーは本物と同じ `campaigns` テーブルに入れ、`provider` を `dummy` にして見分ける（別のテーブルは作らない。API・画面はそのまま使い、本物が入ったらダミーを消すだけで切り替わる）
- 入れる内容: 10件。カテゴリ・対応端末・定額／定率・ポイント・成果地点の数・掲載期間をばらばらにする。1件は掲載期間が終わったもの（お気に入りの「掲載終了」の確認用）。名前の先頭に「【ダミー】」を付ける。トップの案件メニューの確認用に、5件に特集の印（はじめて向け・ゲーム案件特集・みんなで挑戦中）を付ける。アイコンはサイト内の画像
- 計測リンク（`click_url`）は `https://example.com/` にする。「この案件に進む」を押しても本物の広告主には行かない
- 管理画面 A08 案件の上に「ダミー案件を入れる」「ダミー案件をすべて消す」のボタン（どちらも確認あり）。入れるのは、ダミーがまだないときだけ押せる
- 消すときは、ダミー案件に付いたお気に入り・特集の印と「この案件に進む」の記録（`campaign_clicks`）も一緒に消す。ダミー案件に成果が付くことはない（GF Rewards からの通知は `provider` が違うので突き合わない）
- 入れた・消したは操作ログに残す
- 公開前に必ず消す（[14章](#14-まだ決まっていないこと) とは別に、公開前の確認項目）
- 実装: `App\Services\Campaigns\DummyCampaigns`。管理画面のルートは `POST /campaigns/dummies`（入れる）と `DELETE /campaigns/dummies`（すべて消す）。操作ログの種類は `campaign.dummy_insert` / `campaign.dummy_delete`。アイコンは会員サイトのキャラ画像（`POIFO_FRONT_URL` の `/images/mascot/`）

## 5. ポイント

### 5.1 台帳

ポイントは1件ずつの台帳（`point_transactions`）で持ち、残高はその合計で出す。

| 状態 | 意味 | 残高 |
|---|---|---|
| 判定中 | 成果は発生したが、広告主の承認待ち | 「判定中」に数える。使えない |
| 確定 | 使えるポイント | 「利用可能」に数える |
| 否認 | 広告主が否認した | 数えない |

| 種類 | 発生するとき | 履歴の表示 |
|---|---|---|
| 案件の成果 | 成果通知を受けたとき | 案件名・成果地点 |
| 換金 | 換金を申請したとき（マイナス） | 換金（交換先を増やしたら「ポイント交換（<交換先>）」、[7.2](#72-共通の流れ)） |
| 換金の取り消し（返却） | 管理者が換金申請を却下したとき | 換金の取り消し（返却） |
| イベント参加 | 管理者が参加を確認したとき | イベント参加: <タイトル> |
| 運営による調整 | 管理者が手で付与・減算したとき | 運営による調整（理由） |
| 紹介報酬・紹介の初回特典 | 紹介した友達の成果が届いたとき・条件を満たしたとき（[15.3](#153-報酬)） | 紹介報酬／紹介の初回特典 |
| 失効 | 退会したとき | — |

- 会員はポイント履歴で、日時・内容・ポイント・状態を新しい順に見られる（1ページ20件）
- ポイントの有効期限はまだない（[14章](#14-まだ決まっていないこと)。台帳には失効の種類を用意してある）

### 5.2 手動調整（管理画面）

- 付与（正の数）または減算（負の数）。理由（255文字まで）が必須で、会員のポイント履歴に理由も表示する
- 減算で利用可能ポイントがマイナスになる調整はできない
- 調整はすぐに確定する（判定中にはしない）。1回の上限は ±100,000 ポイント
- 退会済みの会員には調整できない
- 操作ログに残す

## 6. 成果通知（GF Rewards のポストバック）

お金に直結するので、上から順に確かめ、どこかで通らなければポイントを確定しない。

1. URL に含めた秘密の文字列。違えば 404
2. 送信元 IP（アプリの許可リスト。本番でリストが空なら全て拒否）。WAF ではパスごとの IP 制限をしない（CloudFront の定額プラン Free の範囲に収めるため）
3. 署名（`hash`、HMAC-SHA256）
4. 取り込み済みの案件情報との突き合わせ。会員・案件・成果地点が見つからない、定額案件でポイント数が違う、定率案件で上限を超える場合は **保留** にする（承認の通知が来ても判定中のまま。自動では解除しない）
5. 成果ID（`cv_id`）が同じ通知は重複として二重に付与しない

| 通知の内容 | 台帳 | ASP への応答 |
|---|---|---|
| 未承認 | 判定中で記録 | `0` |
| 承認 | 同じ成果を確定に | `1` |
| 否認 | 同じ成果を否認に | `0` |
| 退会済みの会員 | 記録だけ | `2` |
| 登録のない会員ID | 記録だけ | `0` |

- 拒否・保留を含めて全件を受信ログに残す
- 次の場合は管理者にメールで知らせる（同じ種類は10分に1通）: パスの文字列・送信元 IP・署名の不一致、保留、処理の失敗、1分間に30件を超える受信
- 保留は管理画面で内容を確認して解除できる（承認済みなら通知のポイントで確定、未承認なら判定中のまま）。会員が見つからない・退会済みの成果は解除できない。解除は操作ログに残す

### 6.1 GF Rewards の送り方（2026-11-26 GF Rewards の回答）

- 同じ `cv_id` で、状態（未承認・承認・否認）が変わるたびに通知が届く。順番が前後することはまれにある
- 案件の途中段階（アプリのインストール、会員登録、ゲームの各ミッションなど）は、**成果地点ごとに別の通知**として届く。通知には成果地点ID・成果地点名が入る。インセンティブが0の成果地点も通知される
- 応答の待ち時間は10秒
- HTTP 200 以外を返すか、10秒で応答しないと、10分おきに最大4回やり直す（初回から最後まで約40分、計5回）
- HTTP 200 で本文 `0`（ポイント未付与）を返した通知はやり直さない。このため、未承認・否認・会員なし・保留に `0` を返しても通知が繰り返されることはない
- こちらは処理に失敗したときだけ HTTP 500 を返し、やり直してもらう（それ以外は200で `0`／`1`／`2`）

### 6.2 届かなかった通知の確かめ方と再送

- 5回とも届かなかった通知は、GF Rewards から自動では送り直されない。**こちらから依頼すれば再送してもらえる**
- 取りこぼしは、GF Rewards のレポートの「日別の成果件数」CSV（キャンペーン単位・成果地点単位）と、こちらの受信件数を日ごとに比べて見つける
  - 成果1件ごとの一覧は GF Rewards 側にもないので、どの成果が届いていないかまでは分からない
  - レポートへの反映には時間差があるので、直近の数字は比べない
- 差があったら、成果の発生日・キャンペーン・成果地点を GF Rewards に伝えて確認と再送を頼む
- 1人の会員がどの成果地点まで進んだかを調べたいときは、会員ID（`uid`）を伝えれば GF Rewards が調べてくれる（成果地点として設定されていない進み具合は GF Rewards にも分からない）

### 6.3 サーバのメンテナンス中

- アプリをメンテナンス表示にしても、`/postback/` だけは受け付け続ける（実装済み）
- **GF Rewards に通知を止めてもらわない**。止めている間に発生した通知は、後から再送してもらえないため
- サーバを止める作業は、止まる時間が40分（6.1 のやり直しが続く時間）を超えないようにする。40分を超えそうな作業は、スナップショットから新しいサーバを作り、静的 IP を付け替えて切り替えることで、止まる時間を短くする
- それでも届かなかった通知は、6.2 の手順で再送を頼む

## 7. ポイント交換（換金）

いまの交換先は「銀行振込（現金）」だけ。交換先は後から増やす前提で、**増やしても既存の会員・申請・画面に影響が出ない作り**にする（2026-11-22 yamada）。

> バックエンドは [7.5](#75-銀行振込だけの作りから直したこと) のとおり交換先を単位にする作りに直した（PR #31）。会員サイトの交換先一覧（画面仕様 S12）は、交換先が2つ以上になったときに作る。

### 7.1 交換先の考え方

交換先（例: 銀行振込、ギフト券、電子マネー）ごとに、条件と処理のしかたを設定として持つ。申請・台帳・状態の流れは全交換先で共通にし、交換先ごとに違うところだけを差し替える。

| 交換先ごとに持つ設定 | 内容 | 銀行振込の今の値 |
|---|---|---|
| 交換先コード | 変えない識別子。申請に保存する | `bank_transfer` |
| 表示名・説明・アイコン | 交換先一覧に出す | 銀行振込（現金） |
| 短い名前 | ポイント履歴など、括弧の中に入れる所で使う | 銀行振込 |
| 状態 | 受付中／受付停止（一覧には出すが申請できない）／非表示 | 受付中 |
| 最低ポイント・刻み・1回の上限 | 申請できるポイントの条件 | 1,000P から、1P 刻み、上限なし |
| 交換レート | 1ポイントあたりの価値 | 1P＝1円 |
| 手数料 | 定額・定率・なし | なし（運営負担） |
| 審査期間 | 申請から承認できるまでの日数 | 7日 |
| 受け取り情報 | 申請に必要な会員の情報（なしもあり） | 振込先口座（7.4） |
| 完了のしかた | 人の手で処理して完了にする／外部の API で発行する など | 人の手で振込 → 振込済み |
| 表示順 | 交換先一覧の並び | 1 |
| カテゴリ | 交換先一覧の分け方（現金・ギフト券・電子マネーなど）。2種類以上になったら一覧をカテゴリで分ける | 現金 |
| 受け取りまでの目安 | 交換先一覧・詳細に出す | 月1回まとめて振込 |

- 交換先の条件を変えても、**変える前に出た申請には影響しない**（申請した時点のレート・手数料・受け取り情報を申請に保存する）
- 交換先を止めるときは新しい申請だけ止め、手続き中の申請は最後まで処理する
- ある交換先の条件を変えたり、交換先を追加したりしても、ほかの交換先の条件は変わらない
- 交換先コードは一度使ったら変えない・使い回さない（過去の申請・履歴が指しているため）

### 7.2 共通の流れ

| 状態 | 意味 | 会員への表示（銀行振込の場合） |
|---|---|---|
| 申請中（requested） | 会員が申請した。審査期間中は承認できない | 審査中 |
| 承認済み（approved） | 管理者が承認した。処理待ち | 振込準備中 |
| 完了（paid） | 処理が終わった（振り込んだ・発行した） | 振込済み |
| 却下（rejected） | 管理者が却下し、ポイントを戻した | お振込みできませんでした（ポイント返却済み） |

状態の種類は全交換先で共通。会員への表示の言葉は交換先ごとに変えてよい（ギフト券なら「発行済み」など）。

1. 会員が交換先を選び、ポイントを入力して申請する
   - その交換先の条件（最低ポイント・刻み・上限）を満たし、利用可能ポイントを超えないこと
   - その交換先に受け取り情報が必要なら、登録していないと申請できない
   - 停止中の会員・受付停止の交換先は申請できない
   - 申請した時点のレート・手数料・受け取り情報を申請に保存し、ポイントを台帳から引く
   - 回数制限は全交換先の合計で1分3回・1日10回
2. その交換先の審査期間が過ぎるまでは承認できない
3. 管理者が申請を確認して承認する（不審なものは却下 → ポイントを戻す）
4. 交換先ごとの方法で処理し、完了にする
5. 承認・却下・完了・出力は操作ログに残す

- ポイント履歴には「ポイント交換（<交換先の短い名前>）」と出す。却下で戻したときは「ポイント交換の取り消し（返却）」。この表示は直した後の新しい申請からで、前からある履歴は「換金」のまま
- 退会できない条件は「どの交換先でも、手続き中（申請中・承認済み）の申請があるとき」
- 将来の自動振込・外部 API での発行はこのサーバでは行わない方針（別の仕組みから申請を読み、完了を書き戻す形を想定）

### 7.3 銀行振込（現金）の処理

当面の唯一の交換先。月1回、運営が人の手で振り込む。

1. 月末に管理者がその月の銀行振込の申請を確認し、まとめて承認する
   - 一覧では同じ口座・同じ名義がほかの会員にあると警告を出す
2. 「承認済み」の申請を振込用 CSV で出力する（UTF-8 BOM 付き・CRLF。Excel で開ける）
   - 列: 申請ID・申請日時・会員ID・氏名・口座名義カナ・銀行コード／名・支店コード／名・口座種別・口座番号・換金ポイント・換金額・手数料・振込額・状態・注意
   - 口座番号の全桁が出るのはこの CSV だけ
3. 銀行で人の手で振り込み、振り込んだ申請を選んで「振込済み」にする

### 7.4 銀行振込の受け取り情報（振込先口座）

| 項目 | 入力のルール |
|---|---|
| 氏名（漢字） | 必須、60文字まで |
| 金融機関名・金融機関コード | 必須。コードは数字4桁 |
| 支店名・支店コード | 必須。コードは数字3桁 |
| 口座種別 | 普通／当座／貯蓄 |
| 口座番号 | 数字7桁以内。DB では暗号化する |
| 口座名義（カナ） | 必須、カタカナ（全角・半角）と全銀で使える記号だけ |

- 1人1口座。登録後も変更できる（1分3回・1日5回まで）
- **ほかの会員が登録済みの口座は登録できない**（不正対策）
- 画面では口座番号を末尾3桁以外伏せて表示する

### 7.5 銀行振込だけの作りから直したこと

交換先を追加する前に、今の銀行振込を「交換先の1つ」として扱う形に直しておく。**既存の会員・申請・URL・API の使い方は変えない**。

PR #31 で実装した（2026-11-22）。実装で決まったこと:

- 交換先の設定は `config/poifo.php` の `exchange_methods`
- 申請に `exchange_method`（交換先コード）・`yen_per_point`（申請時点のレート）・`recipient_snapshot`（受け取り情報の控え）を保存する。`bank_snapshot` の中身は `recipient_snapshot` に移して列を消した
- `GET /v1/exchange-methods` はログインなしで使える。非表示の交換先は返さず、受付停止の交換先は `accepting: false` で返す
- 換金申請の履歴 API と、ポイント履歴（`GET /v1/me/points`）の各行に `exchange_method`・`exchange_method_name` を足した

下の表は直す前と後の対応。

| 対象 | 今 | 変えた後 |
|---|---|---|
| 交換先の設定 | 最低ポイント・審査期間・レートが環境変数（全体で1つ）、手数料はコードで0円 | 交換先ごとの設定（`config` かテーブル）。銀行振込の値は今と同じにする |
| 申請（`withdrawal_requests`） | 銀行振込だけ。申請時点の口座を `bank_snapshot` に保存 | 交換先コードの列を足す（既存の行は `bank_transfer`）。受け取り情報の控えは交換先に関係ない名前の列にし、既存の `bank_snapshot` の中身を移す。申請時点のレートも保存する |
| 台帳（`point_transactions`） | 種類「換金」「換金の取り消し」 | 種類はそのまま。どの申請か（＝どの交換先か）をたどれるようにし、履歴の表示に交換先名を出す |
| 受け取り情報 | `bank_accounts`（1人1口座） | そのまま使う。新しい交換先で別の情報が要るときは、その交換先用のテーブルを足す（銀行口座のテーブルに混ぜない） |
| 会員 API | `GET/POST /v1/me/withdrawals` | 同じパスのまま。`GET /v1/exchange-methods`（交換先一覧と条件）を足す。申請の `method` は省略したら `bank_transfer` として扱う。履歴の各行に交換先コード・表示名を足す（既存の項目は消さない） |
| 管理画面 | 申請一覧・振込 CSV | 申請一覧に交換先の絞り込みと列を足す。振込 CSV は銀行振込の申請だけを対象にする |
| 処理の切り替え | 銀行振込の処理が `WithdrawalService` に直接書いてある | 共通の流れ（申請・審査・却下・台帳）と、交換先ごとの部分（条件の検証・受け取り情報の控え・完了のしかた・出力）を分ける |

### 7.6 交換先を追加するとき

1. 交換先の設定（7.1 の表）を決める。運営が決めること: 交換レート・手数料・最低ポイント・審査期間・提供元との契約
2. 受け取り情報が要る交換先なら、その登録画面・テーブルを作る
3. 完了のしかた（人の手で処理する場合は管理画面の操作と出力、提供元の API を使う場合はその連携）を作る
4. 交換先一覧に出す。既存の銀行振込の申請・画面・条件はそのまま

| 項目 | 必須 | 内容 |

| タイトル | ○ | 100文字まで |
| 開始日時 | ○ | |
| 終了日時 | | 開始日時より後 |
| 形式 | | 「オンライン」など。50文字まで |
| 概要 | | 一覧のカードに出す。200文字まで |
| 本文 | | 詳細ページに出す |
| 注意事項 | | 詳細ページに出す |

| 参加上限人数 | | 空なら上限なし |

- 下書きはサイトに出ない。公開にするとイベント一覧・詳細に出る
- 終了日時（なければ開始日の終わり）を過ぎた公開中のイベントは、自動で「終了」として扱う（一覧に残し、詳細に「終了しました」と出して参加ボタンを消す。トップには出さない）。運営が手で「終了」にしてもよい

- 登録・変更・削除は操作ログに残す

### 8.2 参加の管理

参加したかどうかは専用のテーブル（`event_participants`、イベントと会員の組で1行）で判定する。

1. **参加する**: 会員がイベント詳細の「参加する」を押す（ログイン必須）
   - 公開中で、開始前のイベントだけ参加できる
   - 参加上限人数に達していたら「満員」で受け付けない（同時に押されても上限を超えないよう DB のロックで数える）
   - 停止中・退会済みの会員は参加できない
   - 参加すると、オープンチャットの URL が表示される
2. **参加をやめる**: 開始前なら会員が自分で取り消せる（枠が空く）。取り消し後にもう一度参加してもよい
3. **参加の確認とポイント付与**: イベント後に管理画面の参加者一覧で、実際に参加した会員を選んで「参加を確認」する
   - 参加ポイントが設定されていれば、その場で確定ポイントとして付与する
   - 1人1イベント1回だけ付与する（二重付与しない）
   - 参加しなかった会員は「不参加」にできる（ポイントなし）
   - 操作ログに残す

| 参加の状態 | 意味 |
|---|---|
| 参加予定（joined） | 会員が参加ボタンを押した |
| 取り消し（cancelled） | 開始前に会員が取り消した。上限人数に数えない |
| 参加済み（attended） | 管理者が参加を確認した。参加ポイントを付与済み |
| 不参加（absent） | 管理者が不参加とした |

- 一覧・詳細には「残り◯人」（上限があるとき）と、自分が参加予定かどうかを出す
- 管理画面の参加者一覧は CSV でも出せる（会員ID・表示名・状態・参加日時。個人情報は含めない）

## 10. 不正対策・セキュリティ

GF Rewards から換金系サイトとして求められている対策と、その実装。

| 対策 | 実装 |
|---|---|
| 1人1アカウント | LINE アカウントごとに1会員。LINE は電話番号認証済みのため一部カバーできる |
| 退会者の再登録防止 | 退会後も LINE のユーザーIDを残して照合する |
| 同じ口座の複数会員を禁止 | 口座の登録時に拒否する（銀行振込） |
| 名義の重複を検知 | 換金申請の一覧で、同じ口座・同じ名義を警告する |

そのほかの守り:

- 成果通知の多重チェック（[6章](#6-成果通知gf-rewards-のポストバック)）
- 回数制限: 会員 API 全体は1分120回、口座の登録・変更は1分3回・1日5回、換金申請は1分3回・1日10回、LINE ログインの入口は IP ごとに5分50回、案件への遷移は1分30回（いずれもアプリで制限）。WAF は IP ごとの全体の回数制限（API 5分1,000回、管理画面 5分500回）
- 管理画面は IP 制限＋二要素認証
- 口座番号は暗号化して保存する

## 15. 友達紹介（2026-11-28 先方案を受領、条件は仮）

先方の「紹介制度・開発仕様書」（2026-11-27、共有フォルダ `brand/redesign/referral/`）を、今の仕組みに合わせて書き直したもの。**数字や条件の多くは仮**。GF Rewards・広告主が認める前提で実装を進める（2026-11-28 yamada さん）。仮の数字は設定で変えられるようにし、公開前に [14章](#14-まだ決まっていないこと) #19〜#22 で確定する。

### 15.1 考え方

- 会員ごとに紹介コードと紹介URLを持つ。紹介URLから新しく登録した人を「紹介した友達」として記録する
- 紹介した友達が案件で**確定**したポイントに応じて、紹介した人に「紹介報酬」を付ける（継続報酬）。登録しただけでは付かない
- 紹介した友達が条件を満たしたとき、一度だけ「紹介の初回特典」を付ける
- 報酬は**ポイント（P）**で、今のポイント台帳（[5.1](#51-台帳)）に入れる。円で別に管理しない（先方案は「円」表記だが、サイトの単位は2026-11-28 に P に統一。1P＝1円）
- 紹介は一段だけ。友達の友達からは報酬を付けない

### 15.2 紹介のひもづけ

1. 紹介URLは `https://poifo.com/invite/?code=<紹介コード>`。紹介コードは会員ごとに英大文字と数字の8文字（紛らわしい 0・O・1・I は使わない）。初めて紹介ページを開いたときに発行する
2. 紹介URLを開くと、紹介コードをブラウザに30日保存し、紹介ページ（画面仕様 S26）を出す
3. LINE ログインで**新しく会員になったとき**だけ、保存した紹介コードの会員を紹介元として記録する（フロントが「LINEでログイン」の入口に `?ref=<紹介コード>` を付け、API がログインの間セッションに持つ。ログインが終わったらブラウザの紹介コードは消す）。すでに会員の人は紹介元を後から付けられない。紹介元は登録後に変えない
4. ログイン画面（S06）でも紹介コードを入力できる（口頭で伝えた場合のため。任意）
5. 次の場合は紹介元を記録しない: コードが存在しない、紹介元が退会・停止中、自分のコード

### 15.3 報酬

| 種類 | 付けるとき | ポイント（仮） |
|---|---|---|
| 紹介報酬（継続） | 紹介した友達の「案件の成果」が確定したとき | 確定したポイント × 紹介した人のランクの率。1P 未満は切り捨て |
| 紹介の初回特典 | 紹介した友達の確定した「案件の成果」の合計が、登録から180日以内に1,000P 以上になったとき（一度だけ） | 100P |

- 紹介報酬の元にするのは「案件の成果」のポイントだけ。イベント参加・運営による調整・紹介報酬は元にしない
- 友達の成果が「判定中」の間は、紹介報酬も「判定中」で台帳に入れ、成果が確定・否認したら同じく確定・否認にする（残高の数え方は今の台帳と同じ）
- 率は**成果が確定した時点のランク**で決め、あとでランクや率が変わっても確定した報酬は変えない
- 案件ごとに「紹介報酬の対象外」「率の上限」を管理画面で設定できる（採算の合わない案件のため）
- 同じ成果から二重に付けない（成果と報酬の種類の組で1件だけ）
- 紹介した人が退会・停止中のときは付けない。紹介した友達が退会しても、それまでの報酬はそのまま
- 確定したあとで成果が取り消された場合の扱いは、GF Rewards が取り消しを通知するかの確認待ち（14章 #18）。通知が来る場合は、紹介報酬も否認にする

### 15.4 ランク

| ランク | 紹介報酬の率（仮） | 条件（仮） |
|---|---|---|
| レギュラー | 5% | 全会員 |
| ゴールド | 8% | 有効な紹介30人以上 |
| プラチナ | 10% | 有効な紹介100人以上 |
| 特別パートナー | 個別（上限15%） | 運営が管理画面で指定（招待制。初期5名程度） |

- 「有効な紹介」＝紹介した友達のうち、初回特典の条件を満たした人（退会・停止中の人と、運営が紹介を無効にした人は数えない）
- 一般のランクは有効な紹介の人数から毎回計算する（下がる条件・集計期間は14章 #19）。特別パートナーは自動の昇格とは別で、運営が付ける・外す
- ランク（名前・率・必要な有効紹介人数）と初回特典（ポイント・条件のポイント・期限の日数）は **管理画面で変える**（A17。2026-11-28 yamada さん）。DB に持ち、変えた内容は操作ログに残す。変えても確定した報酬はさかのぼらない（判定中の報酬は、確定した時点の設定で計算する）
- ランクは増やす・減らすこともできる（特別パートナー以外。会員がいるランクを消すと、その会員は人数に応じて下のランクになる）。率は0〜100%

### 15.5 会員に見せるもの・見せないもの

- 見せる: 紹介コード・URL、ランクと率、次のランクまでの人数、累計の紹介人数・有効な紹介人数・今月の紹介人数、今月確定した紹介報酬・判定中の紹介報酬、紹介報酬の履歴
- 見せない: 紹介した友達の名前・LINE の情報・どの案件を使ったか
- 紹介報酬はポイント通帳（S09）の明細にも「紹介報酬」「紹介の初回特典」として出る

### 15.6 不正対策

- 禁止事項（自分を紹介する、複数アカウント、虚偽の勧誘）は利用規約に書く（14章 #4 の本文に追加）
- 紹介した人と紹介した友達の振込先口座が同じ・同じ名義のときは、管理画面で警告を出す（[7章](#7-ポイント交換換金) の同一口座の警告と同じ考え方）
- 管理者は紹介を「無効」にできる（理由必須、操作ログに残す）。無効にすると、それ以降の報酬は付かず、判定中の報酬は否認にする。無効はその会員が「紹介した人」「紹介された友達」のどちらの立場にも効く（不正が紹介した側・された側のどちらにあっても止められるように）。無効にした会員の紹介コードでは、新しい紹介も記録しない。無効は取り消せるが、否認にした報酬は戻さない

### 15.7 管理画面

- 会員詳細（A07）: 紹介コード、紹介元、紹介した人数・有効な人数、ランク。特別パートナーの指定・解除と率（理由必須）。紹介を無効にする
- 案件（A08）: 紹介報酬の対象外、率の上限
- 紹介の設定（A17、新規）: ランクごとの名前・率・必要な人数、特別パートナーの率の上限、初回特典のポイント・条件・期限
- 紹介報酬（A16、新規）: 紹介した人・紹介した友達・種類・状態・期間で検索。CSV 出力
- 手動の調整は今の「運営による調整」（[5.2](#52-手動調整管理画面)）を使う
